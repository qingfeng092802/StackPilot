# 访谈记录模板（M1 · 输出侧验证）

> 配套材料：`docs/output-validation-preview.md`（给受访者看的方案，不要给这份模板）
> 分析口径：`docs/interview-analysis-framework.md` —— **访谈前不要打开**，它会影响你怎么问
> 一人一份。复制下面「§3 记录表」整块 5 次，编号 R1–R5。

---

## 0. 这份表要拿到什么

只要 4 个数，别贪多：

| 要拿到的 | 从哪一行取 | 拿去干什么 |
|---|---|---|
| 能不能说出**具体第一步** | §4 第 1 题 | 决定 A / B / C 分支 |
| 放弃时的**卡点** | §4 第 2 题 | 分因：看不懂 / 不认同架构 |
| **看不懂的词** | §4 第 3 题 | 同上，且优先级更高 |
| 画像（非技术/半技术/全栈） | §3 表 | 分组对比，看问题是格式还是内容 |

**不要收集**：满意度打分、NPS、"你觉得有没有用"、愿不愿意付费。这些在 n=5 时全是噪音，而且会诱导对方说好话。

## 1. 开场话术（照读，别自由发挥）

> "我在验证一个想法，不是卖东西。这是一份给你这种需求的架构建议，你先自己看两分钟，我不解释，看不懂的地方就是它的问题不是你的问题。看完我问三个问题，大概十分钟。"

三个必须做到的点：

1. **说"我在验证一个想法"**，不说"这是我做的产品"。后者会让对方照顾你情绪。
2. **明确"我不解释"**。一旦你开始解释，你测的就不是材料，是你本人的讲解能力。
3. **明确"看不懂是它的问题"**。否则对方会把"没看懂"包装成"挺好的"。

---

## 2. 交互纪律（每次访谈前逐条打勾）

- [ ] 先给方案，**给完就闭嘴**，不主动介绍这套技术是干什么的
- [ ] 给完至少**留 60 秒沉默**，让对方面对材料，不打破沉默
- [ ] **不问"你觉得好不好 / 有没有用 / 靠不靠谱"**（这三个问题只会得到"挺好的"）
- [ ] 对方卡住时**不帮补话**，不提示"是不是因为……"，只重复原问题
- [ ] 对方说出技术判断时**不辩护、不纠正**，只记原话
- [ ] 三题按顺序问，**逐字照读**，不改词、不追加解释、不缩减
- [ ] 全程**录音或速记原话**，不当场总结成"他觉得太重"
- [ ] 访谈中**不打开** `interview-analysis-framework.md`

> **顺序很重要**：`output-validation-preview.md` 每个案例末尾有 3 个「案例专属问题」（问架构判断认不认同）。
> 那 3 个问题是**引导性**的，必须放在本模板的**通用三题之后**问。
> 先问专属问题，等于提前把答案喂给对方，第 1 题就废了。

## 4. 三题原话（必须逐字，不许改词）

> 以下三题**照读**。括号里是"记什么"，不是"怎么问"。

| # | 问题（原样问出） | 受访者原话（逐字） |
|---|---|---|
| 1 | "你看完这个方案，今晚会去做的第一步具体是什么？" | |
| 2 | "如果你现在要放弃这个方案，最可能是因为哪个卡点？" | |
| 3 | "方案里有没有哪个词/哪句话你没看懂？" | |

**第 1 题的追问规则**（只在对方答得含糊时用，且只能追一次）：

- 答"先学一下 React"→ 追一句：**"今晚具体打开哪个网站、做什么动作？"**
- 答"再想想 / 先调研"→ 追一句：**"那今晚会打开什么？"**
- 追问后仍然说不出具体动作 → 记为**未达标**，不要第三次追问

## 5. 判定：第一步算不算"具体"

访谈当场就要判，不要回家再判（回家会往好处判）。

| 判定 | 口径 | 示例句式（仅校准口径，不是访谈数据） |
|---|---|---|
| **达标** | 有**具体工具/具体网站/具体命令**，且是**建设性动作**（注册、建项目、装依赖、跑模板、写第一个页面） | "去 Vercel 注册个号"／"先建个 Supabase 项目拿 key"／"把 Next.js 模板 clone 下来跑起来" |
| **半步** | 指向具体对象，但动作是**决策/确认**而非建设 | "先去搜一下 Next.js 和 Vite 的区别"／"先看看 Supabase 国内能不能连" |
| **未达标** | 泛指学习、泛指调研、泛指思考，**没有具体对象** | "先学一下前端"／"再看看文档"／"先把需求理清楚"／"找个时间研究下" |

记录：

| 项 | 记录 |
|---|---|
| 第 1 题判定 | ☐ 达标　☐ 半步　☐ 未达标 |
| 判定依据（引用原话里的哪个词） | |
| 有没有对上"今晚"这个时间框（说了"这周/以后"→ 降一档） | |
| **是否全盘采纳** | ☐ 全盘照做　☐ 降档减配　☐ 不适用（案例没给方案） |
| 降档的话，他砍掉了什么（原话） | |

> **只有"达标"进 A 分支的分子。"半步"单独计数，用来做辅助信号，不进分子。**

> **「是否全盘采纳」为什么不进 p，却必须记**：
> 它测的不是"会不会动手"，是"方案的默认值准不准"。
> 第二轮访谈里 4 个达标者有 3 个会砍掉方案的一部分（砍数据库 / 换框架 / 评估学习成本），
> **没有一个人说"你给得太简单了"**——所有人都在往轻里砍。这是"默认值偏重"的直接证据，
> 比 p 值更能指导下一步该调什么。完整论证见 `docs/interview-round2-analysis.md` §5.2 / §8。

## 6. 卡点归类（第 2、3 题合起来判，只选一个主因）

| 主因 | 判定信号 | 勾选 |
|---|---|---|
| **看不懂** | 第 3 题点出了**架构名词**（Next.js / Supabase / Vercel / PostgreSQL / Edge Functions）；或第 2 题说"不知道从哪下手"但说不出具体不懂什么 | ☐ |
| **不认同架构** | 第 3 题只有实现细节词（RLS / 连接池 / service_role），且第 2 题明确说"太重 / 不想用 X / 我想要纯静态" | ☐ |
| **不信任** | 第 2 题说"这方案靠谱吗 / 会不会白学 / 出了问题谁管" | ☐ |
| **能力不匹配** | 第 2 题说"我连 JS 都不会 / 我只会 Python" | ☐ |
| **没有动机** | 第 2 题说"我其实没这个需求 / 我就随便问问" | ☐ |
| **其他**（写下来） | | ☐ |

> 主因判定有优先级：**没有动机 > 看不懂 > 不认同架构**。
> 前两个是上游问题，上游没解决，下游的"不认同"没有解释力。
