## 一、这个 ADR 要回答什么

M0 的验收问题只有一个：

> **「用户需要技术栈选型，并且愿意照着给出的方案开始」这个产品假设，是否值得进入 M1 继续投入？**

拆成三个可测的子问题：

| 子问题 | 对应指标 | 本轮结论 |
|---|---|---|
| 输入侧：这种需求真实存在吗？ | D1 产出率、闭集覆盖率 | **成立**（见 §3、§5） |
| 引擎侧：给出的方案对不对？ | DB 判断 / 服务端层判断 / 框架判断 | **7/7 ｜ 3/7→6/7 ｜ 1/7**（见 §6） |
| 输出侧：用户会照着做吗？ | —— | **完全没有验证**（见 §10） |

关键判断：**前两个问题有数据，第三个问题一条证据都没有。** 这一条决定了本 ADR 的结论必须是"有条件"的。

## 二、证据基础，以及它的局限

| 项 | 数字 | 说明 |
|---|---|---|
| 抓取帖子 | 60 条 | V2EX `/go/create` 第 1–3 页 |
| 其中独立产品 | 51 条 | 其余为讨论/求助/非产品 |
| 可深读样本 | 10 条 | 27 条有技术栈线索 → 8 条过字段门槛 → 加早期深读 2 条 |
| 可判定（出了方案） | 7 条 | 另 3 条因交付形态超出闭集被 BLOCKED |

**局限（必须先说清，否则下面的百分比会被误读）：**

1. n=7。严格命中率的 Wilson 95% 置信区间是 **[2.6%, 51.3%]**——这个区间宽到无法支撑任何结论。**命中率不能作为 Go/No-Go 的判据。**
2. 样本来自单一社区（V2EX），且是"已经做完了的人"的复盘帖，不是"正在纠结选什么"的人。存在幸存者偏差。
3. 盲标协议要求第一遍禁止看技术栈，已执行；但标注者与实现者是同一主体，无法排除"我知道引擎怎么打分"的隐性影响。
4. 闭集覆盖率 n=51，区间 [34.1%, 60.5%]，相对可用。

## 三、D1 的真实产出率：29.6%，以及它为什么这么低

**27 条真实「我做了个产品」帖里，只有 8 条（29.6%，Wilson 95% CI [15.9%, 48.5%]）同时满足「≥6/9 字段可判定」+「正文明确写了技术栈」。**

这个数字不是筛选标准定得太严，是这类内容的客观分布：

1. **"求技术栈"这个动作本身几乎不以帖子的形式存在。** 4 轮检索 + 6 次抓取，命中真实原帖 **0 条**。这类需求的典型形态是：标题无关键词（"想做个 xxx，求建议"）、正文口语化、无外链——SEO 权重极低，检索不到。
2. **作者写复盘时只写"做成了什么"，不写"为什么这么选"。** 51 条产品帖里，只有 27 条能看出用了什么技术。
3. 剩下 8 条能过门槛的，都是因为作者恰好写了取舍理由（"我不想搞后端""文件绝对不能上传"）。

**对产品的含义（重要）**：产出率低不等于需求少，而等于**这个需求不被公开表达**。用户在私下纠结，不在公开场合提问。这直接影响获客路径——M1 不能指望"搜到帖子去回答"，得靠产品形态（工具/问答入口）把人接住。

## 五、三个关键数据洞察

### 洞察 1：C11 通吃不是打分算法缺陷，是 schema 缺槽位（已修）

- **现象**：`required_capabilities = []` 时，零数据库方案 C11 必然最高分。H06 真实是 React + Node + SQLite（**要 DB**），却被推了零数据库方案。
- **机制**：`required_capabilities` 里**没有"数据持久化"这个槽位**。用户说"记一下花销""收藏起来"，标注只能填 `[]`，而 `[]` 被当成"什么都不需要"。真实需求里 `caps=[]` 极常见（10 条里 3 条）。
- **为什么不是算法问题**：C11 的 base_scores 和 fit 乘数都按规则正确执行了。算法没错，是**需求表达不了**。表达力缺一格，算法再对也推错。
- **修法**：补 `data_persistence` 能力 + 从原文关键词推断 + C11 加硬排除 + C01/C02 加 `+1` 对冲。**没有动 C11 的 base_scores，也没有调权重。**
- **结果**：H06 的 C11 被过滤（若不排除它拿 4.51 分，会赢过 C01 的 4.44），Top1 回到带 DB 的 C01。

### 洞察 2：真实需求里最大的一类，闭集一套都没有

- 10 条样本里 **3 条（H02/H05/H08，30%）真实栈是"纯静态/零框架"**——没有 React、没有 Next.js、没有后端，就是 HTML/CSS/JS 加浏览器本地处理。
- 闭集 11 套模板**全是"框架 + 托管"的成套方案**，一套 static 都没有。最近邻只能报"C01，但多了一层 Supabase 托管，且多了一个独立后端服务层"——这句话的意思是：**我们知道它错，但拿不出对的**。
- 更结构性的一点：11 套里 Next.js 占 4 套（C01/C02/C09/C11）。这是"C01 通吃"和"框架命中率只有 1/7"的共同根因——**闭集在框架维度上是偏斜的**。
- **v0.4.3 处置（M1 第一阶段）**：已补 **C12（Vite + React 纯静态，零后端）**，新开范式 E。
  三条用例的 Top1 全部从 C11 变为 C12，"要不要服务端层"的判断从 3/7 升到 **6/7**。
  **但框架层仍未覆盖**——C12 的前端是 Vite + React，真实栈是"无框架纯静态"，
  所以判定标签仍是 PARTIAL_HIT。要让它变 HIT 需要一套"无框架静态"模板（C13），
  本轮按任务要求只加一套，留待 M1 第二阶段。

### 洞察 3：Schema 的三个表达缺口（已补）

| 缺口 | 真实影响 | 本轮状态 |
|---|---|---|
| `skills` 只有 js/python/sql/ops | 10 条里 4 条作者用 Go/Rust/Java/Bun，只能记 null 或用近似值，系统性压低其匹配度 | 已补 go/rust/java 槽位（`strongestLang()` 未改，见 §10） |
| `delivery` 没有 cli / selfhost | H09（命令行 + MCP）只能记 null，H10（自部署到 NAS）只能勉强记 web | 已补枚举；`cli` 判 uncovered、`selfhost` 判 covered |
| `required_capabilities` 的 `file` 语义歧义 | "用户上传文件"和"服务端要存文件"共用一个值。H08 若标 `file`，C11 会被硬排除——而作者的真实约束恰恰是"不要服务端" | 已拆 `file_upload` / `file_storage`，旧值保留为别名（别名偏严，见 §10） |

## 六、能力边界：DB 判断 7/7，服务端层 3/7→6/7，框架 1/7

> **v0.4.3 更正**：本节初稿把「要不要数据库」和「要不要独立后端」合成一条，写成「分层判断 7/7」——
> **这是错的**。7/7 只是「要不要数据库」；「要不要服务端层」当时只有 **3/7**：
> H01/H02/H05/H08 四条的真实栈都没有独立后端，而引擎推的 C11 带着 BE-01 Route Handlers。
> 错因很具体：当时只核了 `has_db` 一个字段就下了"分层全对"的结论，没核 `has_separate_backend`。
> 下面给出更正后的三行，以及加入 C12 之后的变化。

| 判断维度 | M0 结束时 | 加入 C12 后 | 说明 |
|---|---|---|---|
| 要不要数据库 | **7/7** | 7/7 | 真实有没有 DB，引擎全判对 |
| 要不要服务端层 | **3/7** | **6/7** | 只有 H04/H06/H10（本来就要后端）判对；H01/H02/H05/H08 被判成"多了一层" |
| 用哪个前端框架 | **1/7** | 1/7 | 只有 H01 对上（Next.js）；其余真实是 static（3 条）、unnamed（2 条）、react-spa（1 条） |

**C12 修的就是第二行。** 旧闭集 11 套**全部**带 `be` 组件（连零数据库的 C11 也有 Route Handlers），
所以"纯静态"这个答案在闭集里根本不存在，引擎只能把 H02/H05/H08 推向"多一层"的方案。
补 C12 后服务端层判断从 3/7 升到 6/7；框架判断仍是 1/7，因为 C12 的前端是 Vite + React，
而真实栈是"无框架纯静态"，框架家族依然对不上。

剩下的那 1 条（H01）属口径边界，不是推荐错误：真实栈是 Next.js 单进程，C11 的 BE-01 是同一进程内的
Route Handlers，"算不算多一层服务端"取决于定义。这条不打算靠加模板解决。

**含义**：引擎能可靠回答"要不要数据库"（7/7），能基本回答"要不要服务端层"（6/7），
但答不好"用 React 还是 Vue"（1/7）。前两个选错的代价是**推倒数据层重来**，第三个只是**重写页面**。
这个能力分布正好对应产品的承诺边界（PRD v0.4.3 §2.1），也是"先定架构、不替你选框架"这句话的数据依据。

## 七、Go/No-Go 建议

> **建议：Conditional Go —— 允许进入 M1，但 M1 的核心任务不是接 LLM 管线，而是「补闭集 + 验证输出侧」。**

支持 Go 的理由：

1. **需求真实存在，且用户在裸奔。** 51 条产品帖里 27 条能看出技术栈，说明这个决策人人都在做；但其中大量选择是被"网上教程说 Next.js 好"带过去的，不是按约束推出来的。H04（10 年合租车经验、用过十几款工具）都要自己造，说明现成方案不匹配的场景是真实存在的。
2. **引擎在两个高价值粒度上已经可靠**：要不要数据库 7/7、要不要服务端层 6/7（补 C12 后）。
   这个粒度足够支撑一个"先帮你定架构，再告诉你具体用什么"的产品。
3. **架构上已经能脱离 LLM 跑通**：`scoring.ts` 是纯函数，`d3-harness.ts` 已经能产出 `out/d3-input/*.json` 全套结构化方案。LLM 只负责把结构化结果写成人话——**它不是卡脖子环节**。

不支持"直接放开做"的理由（这就是"有条件"的部分）：

1. **输出侧零证据。** 产品假设的后半句是"愿意照着开始"，我们连一个用户看到方案后的反应都没有。D1 只证明了输入侧。
2. **闭集覆盖率 47.1%，无法表达 43.1%。** 一半的真实需求连候选都进不去——这不是精度问题，是**没有产品**。
3. **命中率样本量不足以做判据**（n=7，CI [2.6%, 51.3%]）。用 14% 或 57% 来说"模型行/不行"都是自欺。

## 八、如果 Go，M1 的任务排序

**不要按"技术依赖顺序"排，按"证伪成本"排。** 越能早死的事越先做。

### 第 1 优先：扩闭集，把覆盖率从 47.1% 拉到 60%+

> **v0.4.3 更正（验收口径，重要）**：这条最初的验收写的是"Q1 覆盖率 ≥ 60%"，**口径错了**。
> `d1-coverage.ts` 的 Q1 只看「真实产品的 `delivery_form` 是否在覆盖集合 `{web, miniprogram, selfhost}` 内」，
> 补 static / SPA 模板**不会让它变化**——实测加完 C12 后仍是 **47.1%**。
> 要让 Q1 动，只能补 **desktop / CLI / 插件** 这类**新交付形态**的模板，那是另一个量级的工程。
>
> 所以本项的验收改为：**「要不要服务端层」判断 ≥ 6/7（已达成 6/7）**，
> 且 `web` 形态内不再出现"闭集里没有零后端方案"这种情况（已消除）。
> 原先写的"至少一条 PARTIAL 变 HIT"**未达成**——因为 C12 的框架是 Vite + React，
> 真实栈是"无框架纯静态"，框架层依然对不上。要达成得再加 C13。

- 补 **2–3 套 static / React SPA 类模板**（H02/H05/H08 这三条真实需求直接指向它）。
- 同时修闭集的框架偏斜：现在 Next.js 占 4/11。至少要让 React SPA 路线有一套能和 C01 正面竞争的模板（现有 C04 被 `expected_users > 1000` 和 `file` 两条硬排除卡得太死）。
- **验收**：`d1-coverage.ts` 的 Q1 覆盖率 ≥ 60%；H02/H05/H08 至少一条从 PARTIAL 变 HIT。
- **为什么排第一**：它同时改善覆盖率和框架命中率，且**不依赖任何未验证的假设**。

### 第 2 优先：验证输出侧 —— 这是真正的 Go/No-Go 判据

- 从这 10 条样本的作者里找 **3–5 个人**（他们已经在做同类产品，是最好的早期用户），把 D3 产出的方案给她们，只问三个问题：
  1. 这个方案你看得懂吗？
  2. 你会照着它开始吗？如果不会，是哪一句让你不想开始？
  3. 你原本打算用什么？看完之后改了吗？
- **验收**：3–5 人里至少 2 人表示"会照着开始"，且能说出具体照着做的第一步。
- **为什么排第二**：它是产品假设的**唯一**判据，但它需要人，周期长，所以要尽早启动、与第 1 项并行。
- **如果这一项失败，第 3 项做得再漂亮也没意义。**

### 第 3 优先：接 LLM 解释管线

- 只有第 1、2 项都过了才值得做。
- 现成的入口是 `M0-D3-方案生成Prompt.md` ＋ `out/d3-input/*.json`，LLM 只做"把结构化方案写成新手看得懂的话"，不参与选型（这条铁律不能破）。
- **为什么排最后**：没有它，产品是"一份 JSON"；有它，产品是"一份人话"。前者能验证假设，后者只是体验优化。

## 九、什么情况下转 No-Go

提前写清楚，避免到时候用"再调调就好了"自我说服：

1. **第 2 项里 3–5 个用户没有一个照着开始** → No-Go，或 pivot 成"选型对比表"（只做信息聚合，不做推荐，降低承诺）。
2. **扩完闭集覆盖率仍 < 55%** → 说明"闭集模板"这条路线本身不成立（真实需求的形态太散），应考虑改成"生成式选型 + 事实层校验"。
3. **「要不要数据库」判断跌到 5/7 以下，或「要不要服务端层」跌回 4/7 以下** → 说明当前可靠性是样本偶然，不是能力。

## 补记二：M0 最终结论 —— Go，且定位收窄（2026-10-23 23:10）

本节取代 §七 的 Conditional Go。§七 保留原文不动，作为决策过程记录。

### 一、两轮真人访谈：8 份样本，只有 5 份可用

| 轮次 | 样本 | 结果 | 处置 |
|---|---|---|---|
| 第一轮 | 3 份 | **案例字段全部错配**——三份记录都描述了 Supabase / RLS / 连接池，而这三个词只在 H06 里出现。实际三人看的都是 H06，H05 / H03 零覆盖 | 数据作废，只留方法学教训（案例核对靠复述名词，不靠事后回忆） |
| 第二轮 | 5 份 | 案例覆盖 3/3、字段核对 5/5 可信。**n=4（剥离 R4）、k=3、p=0.75 → 情况 A** | 作为本次裁决的证据基础 |

**为什么剥离 R4**：H03 是"不出方案"案例。没有方案，"今晚第一步"必然是他自己的计划，
无法归因给输出层。他的达标证明的是行动力，不是输出有效。

### 二、定位正式收窄（本 ADR 的核心裁决）

> **StackPilot 为「有一定代码基础、但对全栈架构迷茫」的人，提供架构定调与防坑指南。**

**明确排除：零基础 / 完全没写过代码的用户。这一格标为「未验证」，且不在 MVP 服务范围内。**

依据不是主观划线，是 p=0.75 的结构：

| 画像 | 达标 |
|---|---|
| 会写代码（半技术 / 全栈） | **3/3** |
| 完全没写过代码 | **0/1** |

3 个达标者**全部**是会写代码的人。唯一的 0 基础受访者接受了架构判断
（"我现在更信这份方案，因为它说纯静态不用花服务器钱"），但断在
"我连第一句 HTML 写在哪里、怎么让它变成一个网页链接我都不会"。

他的原话里还有一条决定性的信号——身边同类"都在想做个人网站或作品集，**但都在等现成工具**"。
**要"帮我做完"的人属于 Lovable / bolt.new 的地盘；要"告诉我用什么做"的人才是我们的用户。**
两者混在一起做，产品会变成四不像。

这条边界已写入 PRD v0.4.4 §2.2，并由 `check-consistency` 断言守住（不允许只写在 ADR 里）。

### 三、H03「不出方案」策略：验证成功，且被明令保护

M0 里唯一一条"反直觉设计被真人明确认可"的证据：

| 问题 | 全栈受访者的回答 |
|---|---|
| 这是在帮你还是敷衍你 | "**是在帮我**。实话实说总比硬套一个 Web 方案、最后发现根本拿不到系统级权限强。不能做就直说，不浪费彼此时间。" |
| 会改形态吗 | "**绝对不会**。剪贴板工具做成网页版就失去了随时快捷键呼出的意义，核心价值就没了。" |
| 愿意留联系方式吗 | "可以留邮箱，如果你们后续能覆盖 Tauri/Rust 的轻量客户端打包方案，我愿意看。" |

PRD v0.4.4 §2.2 已写明：**这条行为在 M1 里不允许为了"提高出方案率"而改成硬凑。**

### 四、`data_persistence` 语义降级（combos v1.5.0）

两个看过 H06 的受访者 **2/2** 认为 MVP 阶段不需要数据库（"LocalStorage 存个 JSON 就够"、
"MVP 阶段这个判断确实偏重"）。旧设计用**一票否决**处理这件事，代价是用户**根本看不到**
"纯静态 + 本地存"这条路存在。

| 项 | v1.4.0 | v1.5.0 |
|---|---|---|
| C11 / C12 | `contains data_persistence` **硬排除** | fit **-1**（C12 净 -2，同时失去"什么都不需要"的 +1） |
| C01 / C02 | fit +1 | fit +1（不变） |
| 用户能否看到零后端方案 | 看不到 | 看得到，排在带 DB 的方案后面 |

**H06 实测**：C11 从"被硬过滤"变成"差一点入选 4.10"，C12 3.70 进入候选；Top1 仍是 C01（4.44）。
**D1 双集全部指标零变化**——降级只改变可见性，不改变结论。

**明确没做的部分**：没有按"数据类型（会话级偏好 / 业务数据）"给 C11 分档 +1 / -1。
引擎当前没有任何数据类型信号，硬造一个没人填的字段会变成死代码——
和 `multi_platform`（从未生效）、`coverage_status = partial`（不可达）是同一类坑。
等 M1 第二阶段接入 LLM、由模型判断数据类型后再启用。

### 七、判定：Go

**M0 结束。进入 M1 第二阶段（接入 LLM 生成解释层）。**

M1 第二阶段的范围：

| 做 | 不做 |
|---|---|
| 接入 LLM 生成解释层（用 `docs/output-validation-preview.md` 的"引擎的输出"那段当格式规范） | 不加 C13 / 不再扩闭集 |
