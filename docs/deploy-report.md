## 0. 一句话结论

**WorkBuddy 应用托管「有条件通过」**：node:http + SSE + 环境变量都能跑，
但**网关会把所有路径重写成 `/`**，必须加一层单路径折叠适配（已实现并默认开启）。
另外三个候选（Vercel / CloudBase·FC / 自建 Nginx）本轮**没有实测**，因为都需要用户侧的云账号凭据。

## 2. 第 1 关：功能兼容

判据原文：**能否部署 node:http + SSE + 环境变量。**

### 2.1 结论

| 项 | 结果 | 备注 |
|---|---|---|
| node:http 单端口 | ✅ | 监听 `PORT`，绑 `0.0.0.0` |
| 环境变量 | ✅ | 沙箱**没有**注入 env 的入口，改为 `boot.js` 在 import 前写入 |
| SSE | ✅ | 真流式，未被网关缓冲 |
| 静态资源 + 多路由 | ❌ **原生不支持** | 网关把所有路径改写成 `/` |

### 2.2 网关路径归一化：实测证据链

这不是猜的，是逐条测出来的。

**① 所有路径到 Node 时都变成 `/`**

用自定义请求头 `x-diag: 1` 触发诊断端点（query 会被网关吃掉，请求头不会）：

| 请求的路径 | Node 收到的 `req.url` |
|---|---|
| `/app.js` | `/` |
| `/a/b/c.js` | `/` |
| `/api/demo` | `/` |
| `/zzz-not-exist` | `/` |
| `/index.html` | `/` |
| `/web/app.js` | `/` |
| `/ICL5KZPNXI/app.js` | `/` |
| `/s/ICL5KZPNXI/app.js` | `/` |
| `/preview/app.js` | `/` |
| `/_/app.js` | `/` |
| `/api/app.js` | `/` |

带 `?sharecode=ICL5KZPNXI` 重试，结果完全一样。

**② 请求确实打到了 Node，不是被静态托管吃掉**

每个响应都带 `x-stackpilot: boot`（应用自己设的响应头）。
`GET /app.js` 返回的是 `text/html` + 首页内容——**是 Node 按 `/` 回的**，不是网关的文件服务。

**③ 请求头里没有任何字段承载原始路径**

诊断端点 dump 的完整请求头：

```json
{
  "x-forwarded-host": "3000-113cc5ed704b4fd981e1a5c8e3cb3ca7.e2b.sg2.sandbox.cloudstudio.club",
  "x-space-key": "113cc5ed704b4fd981e1a5c8e3cb3ca7",
  "x-forwarded-for": "43.174.51.83, 10.4.64.39,::ffff:172.24.0.1",
  "cdn-loop": "TencentEdgeOne; loops=2"
}
```

没有 `x-forwarded-uri`、`x-original-url`、`x-envoy-original-path` 之类的字段。
也就是说：**应用侧拿不回原始路径**，除了改架构没有别的办法。

**④ 沙箱内部是好的，问题在网关**

平台日志：`deploy plan language=node port=3000 start="node boot.js"`，
沙箱内 `curl http://127.0.0.1:3000/` → `PROBE_HTTP_CODE=200`，`service verified`。
所以不是"服务没起"，是网关转发时改写了路径。

### 2.3 处置：单路径折叠适配层

既然网关只认 `/`，那就让应用**只需要 `/`**。

```
GET  /  → 一个把 styles.css 和 app.js 全部内联的单文档 HTML（不再产生子资源请求）
POST /  → 按 body.action 分发：intake / plan / demo
```

实现位置：`server/index.ts` 的「单路径模式」一节，由 `SP_SINGLE_PATH=1` 开启
（`scripts/build-deploy.mjs` 默认写进 `boot.js`）。
业务逻辑**一行没改**，`rank` / `explain` / `intake` 全部原样调用。

前端只加了一层端点解析（`web/app.js` 的 `EP`），三个 fetch 调用点改用 `EP.intake / EP.plan / EP.demo`，
单路径时多带一个 `action` 字段。

**代价（写清楚，不装作没有）**：

| 代价 | 具体影响 |
|---|---|
| 首屏变单文档 | 60,715 B 一次到齐，CSS/JS 无法被浏览器单独缓存，二次访问不省流量 |
| 接口不再 REST | 三个接口共用 `POST /`，只能靠 `body.action` 区分，抓包看不懂 |
| 排查心智负担 | 线上只有一条路径，日志里全是 `POST /` |
| 与本地不一致 | 本地默认多路径，线上单路径。两者行为等价但形态不同 |

**为什么还是接受**：这三条都是"难看"，不是"不对"。而如果不接受，
这个平台上**整个应用不可用**（连 `/app.js` 都拿不到）。

### 2.4 适配后实测

| 用例 | 结果 |
|---|---|
| `GET /` | 200，`text/html`，**60,715 B**，`<style>` 已内联，`__SP_EP__` 已注入，无 `src="/app.js"` 残留 |
| `POST / {action:"demo",state:"high"}` | SSE 7 个事件，跨 **4.2 秒**逐个到达（meta → 5×module → done），**确认未被网关缓冲** |
| `POST / {action:"intake",...}` | 200，1.9s，`ok:true`，`required_capabilities:["no_persistence"]`，`dropped:[]` |
| `POST / {action:"plan",...}` | 200，6.6s，**13 个事件**（meta + 6×progress + 5×module + done），`source:"llm"`，`attempts:1`，`issues:[]` |
| `POST /`（无 action） | 400 + 明确报错文案 |
| 多路径模式（本地 `node server.js`） | `/` 3608B、`/app.js` 39282B `text/javascript`、`/styles.css` 17776B `text/css`、`/zzz` 404、短输入 400、demo SSE 7 事件——**重构未破坏本地开发** |
| **真实浏览器全链路**（Edge headless + CDP） | 输入原文 → 点「开始选型」→ 追问卡出现 → 答语言/目标/团队 → 点生成 → 方案渲染完成。截图 `out/public-plan.png`（1410×2890），Top1 = **Vite + React 纯静态（零后端）** |

最后一行是这一轮最有说服力的证据：它同时验证了**内联单文档能被浏览器正确解析并执行**、
**单路径分发在真实 fetch 下可用**、**SSE 在浏览器里逐块渲染**，以及**极性修复在 UI 上真的产生了不同的 Top1**。
只用 curl 是测不到前两条的——curl 不在乎 CSS 有没有生效、JS 有没有跑起来。

**第 1 关判定：有条件通过。** 条件是必须接受单路径适配层。

## 3. 第 2 关：国内可用性

判据原文：**三网各测 20 次，失败率 > 5% 淘汰。**

### 3.1 实测数据（本机单一网络，未标注运营商）

工具：`node scripts/uptime-probe.mjs --n=20`（成功口径不是"HTTP 200"，而是 200 **且** 正文含 `__SP_EP__`，
防止把"网关 200 返回一张错误页"当成成功）

| 指标 | 值 |
|---|---|
| 样本 | 20 |
| 成功 / 失败 | 20 / 0 |
| **失败率** | **0.0%** ✓ |
| p50 | **1375 ms** |
| p95 | 2245 ms |
| max | 3056 ms |

接口另测 5 次（`--mode=intake`）：5/5 通过，模型耗时 721–1008 ms，端到端 1.1–2.2 s。

### 3.2 两个必须写进结论的观察

**① 沙箱在新加坡，国内访问是跨境。**

`x-forwarded-host` 里的 `e2b.sg2` 是新加坡区域。p50 1.4 s 主要花在跨境链路上，
不是应用处理（应用侧是内存里的静态字符串 + 一次模型调用）。
这一条直接决定第 2 关的天花板：**再优化应用也压不下去**。

**② 有冷启动。**

部署完成后第一次 `GET /` 用了 **5.5 s**，之后稳定在 1.2–3.1 s。
所以"第一次给用户看"要提前预热一次，别让用户撞上冷启动——否则他会以为是产品慢。

**③ 沙箱会空闲自动停止，而且 HTTP 请求唤不醒它。**

这一条是实测撞出来的，必须记下来，因为它**直接影响终测**：

- 表现：打开链接看到的是平台自己的页面——「工作空间已停止 / 数据已保留，可点击下方按钮重新启动以继续工作」，
  错误码 **12809**，下面一行小字写着 SandboxId。
- 连续请求 6 次（每次间隔 6 秒，`--max-time 40`）**全部返回 403 + 那个页面**，不会自己醒。
- 唤醒方式只有两种：用户在页面上点「立即启动」，或者重新部署一次（部署会重启沙箱）。
- 实测空闲约 10–15 分钟就会停。

**对终测的处置**：每次访谈前 5 分钟自己先打开一次链接确认是应用页（不是那个停止页），
并且**把「看到停止页就点立即启动」写进访谈脚本**——否则用户第一次点开就懵，
他反馈的"打不开"会被你误记成产品问题。

### 3.3 第 2 关判定：**未完成**

只测了一个网络，**三网（电信 / 联通 / 移动）覆盖不了**。
这不是"测了没过"，是"没测完"，两者不能混。

补测方法（需要三部不同运营商的手机，各跑一次）：

```bash
node scripts/uptime-probe.mjs --n=20 --label=电信
node scripts/uptime-probe.mjs --n=20 --label=联通
node scripts/uptime-probe.mjs --n=20 --label=移动
```

退出码会在失败率 > 5% 时返回 1，可以直接当判据用。
三份 `label` 不同的输出贴回来，就能把这张表填满。

> 预判：以新加坡节点的跨境延迟看，**移动网大概率是三者里最差的**。
> 如果移动网失败率过 5%，这个候选就该淘汰，转 CloudBase（国内节点）。

## 4. 第 3 关：运维成本

### 4.1 人工步骤数

从"代码改完"到"线上可见"：

| # | 步骤 | 耗时 |
|---|---|---|
| 1 | `node scripts/build-deploy.mjs` | 约 2 s |
| 2 | 调用部署工具（上传 → 沙箱装依赖 → 启动 → 自动 verify） | 约 40 s |
| | **合计 2 步** | 约 45 s |

对比：

| 候选 | 人工步骤 |
|---|---|
| Vercel | 1 步（`vercel --prod`），但首次要登录 + 建项目 |
| CloudBase / FC | 3–5 步（配函数、配触发器、配自定义域名、配环境变量） |
| **自建 + Nginx** | **6+ 步**（买机器、装 nginx、写反代配置、配 systemd、申请证书、开防火墙） |

### 4.2 常驻基础设施数量

| 项 | 数量 |
|---|---|
| 应用进程 | 1（单端口，托管沙箱内） |
| 数据库 | 0 |
| 缓存 / 队列 | 0 |
| 需自己维护的域名 / 证书 | 0（平台给） |
| 需要 patch 的系统组件 | 0 |

### 4.3 隐性成本（这一节才是决策依据）

| 成本 | 严重度 | 说明 |
|---|---|---|
| **凭据必须随产物走** | 🔴 高 | 沙箱没有 env 注入入口，`ANTHROPIC_API_KEY` 只能写进 `boot.js` 跟着代码上传。这是**安全债**：产物一旦泄露 = key 泄露。缓解：key 单独放一个文件、`server.js` 保持干净可单独 review；但这只是把风险隔离，没有消除 |
| **网关改写路径** | 🟡 中 | 已用单路径适配兜住，代价见 §2.3 |
| **沙箱在境外** | 🟡 中 | 跨境延迟，且第 2 关的天花板由它决定 |
| **沙箱不可 SSH** | 🟢 低 | 不能登进去调、不能装系统包、不能看系统级指标。排查只能靠日志和响应头 |
| **单端口** | 🟢 低 | 没有 DB / 缓存 / 队列可挂。当前项目本来就不需要，但以后要加就得外接 |

### 4.4 第 3 关判定：**通过**

2 步人工 + 1 个托管进程，是四个候选里运维最轻的。
但**凭据随产物走这一条必须记在账上**——它是"轻运维"换来的，不是免费的。

## 5. 三关汇总

| 关 | 判定 | 依据 |
|---|---|---|
| 1 功能兼容 | **有条件通过** | node:http / SSE / 环境变量全部可用；多路由必须折叠成单路径 |
| 2 国内可用性 | **未完成** | 单网 20/20、0% 失败、p50 1375 ms；三网未覆盖，且节点在新加坡 |
| 3 运维成本 | **通过** | 2 步人工、1 个托管进程、0 数据库；代价是凭据随产物走 |

**综合：可以用于 M1 终测（10 人小样本），不适合作为长期生产方案。**
理由：终测只需要"用户能打开、能跑通"，0% 失败率已经够；
但新加坡节点 + 凭据在产物里 + 网关改写路径，这三条在真实用户量下都会变成问题。

## 7. 复现方式

```bash
# 构建产物（默认单路径折叠）
node scripts/build-deploy.mjs
# 想要多路径产物（本地调试用）
node scripts/build-deploy.mjs --multi-path

# 本地跑单路径产物（模拟线上形态）
cd deploy && PORT=8899 node boot.js
# 本地跑多路径（模拟本地开发）
cd deploy && PORT=8898 node server.js

# 可用性探针
node scripts/uptime-probe.mjs --n=20 --label=电信
node scripts/uptime-probe.mjs --mode=intake --n=5
```
