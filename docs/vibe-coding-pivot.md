# Vibe Coding 定位偏移：改造评估

> 2026-10-24 · 只写评估，**不改代码**（代码仍冻结在 `ee42ef0`）
> 触发：目标用户从「自己写代码的人」改为「用 Cursor / Agent 写代码的 Vibe Coder」

---

## 0. 一句话结论

**"放弃 skills 字段"是轻改（只碰 9 条规则），但它不会让产品变成 vibe-friendly。**
因为实测下来，`skills` 现在几乎不影响结果——真正把人推向"零后端"的是**权重表**和 **fit 天花板**。
所以这次转向的真实改造量是：**规则轻改 + 权重中改 + 解释层内容重写**。

---

## 1. 先摆事实：`skills` 现在到底影响多少

### 1.1 挂载点（全仓扫描，精确）

| 类型 | 条数 | 分布 |
|---|---|---|
| `fit_rules` 读 `skills.*` | **6 条** | C01×1、C02×1、C03×1、C05×2、C06×1 |
| `hard_exclude_when` 读 `skills.*` | **3 条** | C02（`sql < 0.3`）、C03（`python < 0.3`）、C09（`python < 0.5`） |
| `skillMismatch` 指标 | 1 处 | 只进 `d3-harness` / `smoke-test` 的报告，**不进打分、不进 UI** |

合计 **9 条规则**引用 `skills`。这就是"放弃 skills"要动的全部。

### 1.2 对照实验（同一句需求，只改技能）

输入：`我不会写代码，只想用 Cursor 自然语言让 AI 帮我写，我该选什么技术栈？`
（`delivery=web`、`required_capabilities=[]`、其余字段缺失）

| 技能画像 | Top1 | Top2 | C01 分数 | 被硬过滤 |
|---|---|---|---|---|
| 全 0（js/py/sql/ops = 0） | C12 纯静态 **4.73** | C11 4.73 | **4.05** | C02 / C03 / C07 / C09 |
| 中等（js .8 / sql .4） | C12 纯静态 **4.73** | C11 4.73 | **4.05** | C03 / C07 / C09 |

**技能从 0 改成中等，Top1 没变、C01 分数一分没变。**
唯一差别是 C02（自建 Postgres）从"被排除"变成"能参选"——但它排第 4，进不了 Top2。

> 所以「因为技能为 0，系统排除了 Next.js + Supabase」这个因果**不成立**：
> C01 的硬排除条件只有三条（小程序 / 支付合规 / 用户数 > 1 万），**跟 skills 无关**。

### 1.3 真实成因（按贡献排序）

1. **`goal_type` 缺失 → 权重回落到 `internal_tool`**（`learning 0.39` 最重）。
   用户没回答"做这个是为了什么"时，引擎默认按"内部工具"算，而内部工具最看重上手成本
   → 极简方案天然占优。这是**最大的一股力**，却完全看不见。
2. **fit 天花板不对称**。C11/C12 有一条 `not_contains auth/file/...` 规则，
   需求为空时必然命中 → `fit` 从 4 加到 **5（clamp 上限）**，乘数 1.00。
   C01 的 `base fit` 是 4，**加满也只有 4.45**——数学上赢不了 4.73。
3. **skills=0 只排除了 C02/C03/C09**，这三套本来也进不了 Top2。

**结论：想落地新定位，必须动权重和 fit。只删 skills 字段 ≈ 没改。**

## 2. Q1 · 放弃 skills 后，12 套组合怎么调

### 2.1 三档改动量

| 做法 | 档位 | 涉及 | 是否动基线 |
|---|---|---|---|
| 删掉 9 条 `skills.*` 规则 | **轻** | `combos.json` 9 处 | **否**（Top1 全部不变，已实测） |
| 按模式分叉权重表 | **中** | `scoring.ts` + `combos.json` | 否（只在 vibe 模式生效） |
| 新增"AI 生成准确率"维度 | **重** | 12 套 × 新字段 + 权重表重构 | **是**（全部重算） |

### 2.2 关于"AI 生成准确率 / 训练数据量"作为新权重：**不建议**

四条理由，按重要性排：

1. **不可测**。没有权威数据源，12 个数字只能拍脑袋。而 `combos.json` 里已经有一条纪律
   （`data_honesty`）：*"未核实的结论不得在 UI 中作为确定结论展示"*。
   加一个全靠猜的维度，等于给整张分数表引入一个系统性偏差，且无法被任何测试发现。
2. **会过期**。Cursor 对 Svelte 的支持，半年就变了。写死的分数会从"近似正确"变成"确定的谎话"，
   而且没有任何机制提醒你它过期了。
3. **有先例**。`multi_platform` 这个值曾经在 `combos.json` 里被规则引用、但从未登记进枚举，
   导致那条 `+1` 规则**静默失效两年**（`check-consistency` §8.1 才抓出来）。
   新增一个不可验证的维度，是同一种风险的高级版。
4. **skills 至少可问**。用户能回答"我会一点 Python"；没人能回答"Next.js 的 AI 生成准确率是 4.2 还是 4.5"。

### 2.3 建议的替代：不新增维度，改**权重**

关键观察：**`ecosystem`（生态与文档）本来就是"语料丰富度"的代理。**

- C01（Next.js + Supabase）`ecosystem = 5`
- C12（Vite + React 纯静态）`ecosystem = 4`
- C06（SvelteKit）`ecosystem = 4`

也就是说，"AI 语料最丰富"这件事，**已经在数据里了**，只是被 `learning 0.39` 的权重压住了。

所以最小可行的改法是：**给 `WEIGHTS` 加一组 `ai_assisted` 权重**，
把 `ecosystem` 和 `ops`（托管便捷度）拉到最高，把 `learning` 降下去。

内存模拟结果（未落盘，仅验证算术）：

| | 现在（internal_tool 权重） | 改成 ai_assisted 权重 + vibe fit 规则 |
|---|---|---|
| Top1 | C12 **4.73** | **C01 4.45** |
| Top2 | C11 4.73 | C12 3.88 |
| 第 3 | C01 4.05 | C11 3.88 |
| 技能中等时 | 同上（不变） | 同上（**不变**） |

注意最后一行：**在 vibe 模式下，技能从 0 改成中等，结果完全一样**——这才是"忽略语言熟练度"
真正被验证的样子。

### 2.4 如果只做"删 skills"这一档

- C02/C03/C09 不再被硬排除，候选从 8 条涨到 11 条
- **Top1 不变**（skills 本来就不是成因）
- `skillMismatch` 指标失效（只影响 `d3-harness` 的报告数字）
- 风险：一个真只会 Python 的人会被推 JS 方案。**在新定位下这不是问题**（AI 写），
  但会让 `docs/D1-*` 里的历史基线失去可比性，需要在报告里标注"口径已变"

## 3. Q2 · 解析层 Prompt 怎么改

### 3.1 现在问什么

`MAX_QUESTIONS = 3`，问的是 `skills` → `goal_type` → `team_size`。
其中 `skills` 那题是：**"你最熟的语言是哪个？到什么程度？"**，选项从 `js` 到 `"*"（完全不会写代码）`。

### 3.2 新定位下，"谁写代码"比"会什么语言"重要一个数量级

建议把 `skills` 那一题换成**参与度**问题：

> **这个项目，你打算怎么让 AI 参与？**
> - 我基本不碰代码，全让 AI 写
> - AI 写，我来改和调
> - 我自己写为主，AI 补代码片段

再加一题（决定"第一步"的粒度）：

> **跑报错的时候，你一般能看懂多少？**
> - 能定位到哪一行
> - 只能看出"这里错了"
> - 完全看不懂，只能整段贴回给 AI

第二题不是能力评估，是**决定 first_step 怎么写**：
"打开 supabase.com 建 project" 和 "跑 `npx create-next-app` 然后改 `app/page.tsx` 第 12 行"
是两种完全不同的交付物。

### 3.3 但不要问"你在意自己会不会 JS 吗"

这是**态度题**，会得到社交礼貌答案（"不太在意"），和 M0 那轮踩过的坑一样
（`interview-analysis-framework.md` §8 反模式 #3：*用"用户说挺好"当达标*）。

要问**行为**：

- 你上一次让 AI 写代码，它第一次就跑通了吗？
- 没跑通的时候，你是怎么让它改的？（贴报错 / 描述现象 / 自己动手改）
- 它写的代码你会去看吗？看得懂吗？
- 如果它给你的方案里有 5 个你没听过的名词，你会怎么办？

这四问能直接把受访者分成"纯 vibe"和"AI 写我改"两类，而这两类的最优架构**不同**
（后者需要可读性高、社区大的方案；前者只看"AI 一次能对多少"）。

### 3.4 改动成本：**重**

要动：`intake/prompt.ts`（字段定义 + 3 个 few-shot）、`intake/validate.ts`（新字段的 evidence 闸）、
`intake/index.ts`（追问模板）、`web/app.js`（表单）、`tests/*`（标注数据）。
**不建议现在动**——定位还没被验证，先访谈。

## 4. Q3 · 解释层的"新手坑"怎么演化

### 4.1 现在的坑是"人的坑"

以 C01 为例，三条 `beginner_pitfalls` 原文：

- "Supabase 国内访问不稳定，第一次连不上会误以为是自己代码错了"
- "把 service_role key 写进前端环境变量，会泄露全部数据权限"
- "RLS 没开就上线，任何人都能读到别人的数据"

C03 那条更典型："跨域（CORS）配错，前端一直报 blocked by CORS policy，这是新手第一大坑"。

这些坑的前提是**人会在某个地方写错**。新定位下，写代码的不是人。

### 4.2 要变成"AI 的坑"，而且必须给出**提示词**

| 原（人的坑） | 新（AI 的坑 + 怎么提示它） |
|---|---|
| 把 service_role key 写进前端环境变量 | AI 生成 Supabase 客户端时，常把 `service_role` 直接塞进前端环境变量。提示它："只用 anon key，service_role 只出现在服务端，并给我确认 RLS 已开" |
| RLS 没开就上线 | AI 建表时默认**不开** RLS。让它每建一张表就补一句 `ALTER TABLE x ENABLE ROW LEVEL SECURITY`，并让它列出现有策略 |
| CORS 配错 | AI 会给你 `allow_origins=["*"]`。上线前让它改成具体域名，否则任何人都能跨域调你的接口 |

差别不只是措辞：**原来告诉用户"别犯这个错"，现在告诉用户"怎么指挥 AI 避开这个错"。**

### 4.3 成本：36 条，而且**不能凭空写**

12 套 × 3 条 = 36 条，全部要重写。

更要紧的是：这些内容**必须实测出来**，不能想象。凭空写 AI 的坑，等于编事实——
和解释层最怕的"编一个不存在的坑"是同一件事，只是换了个位置。

建议的最小验证（1 套，约 2 小时）：

1. 拿 C01，用 Cursor 真跑一遍"做个带登录的记账页"
2. 全程录屏，记录它**实际**在哪儿出错、你怎么提示它才改对
3. 从录像里提炼 3 条，必须是"它真的这么干了"的
4. 12 套全做完 ≈ 3 天，但这 3 天换来的是**唯一一份可核实的 AI 坑数据**

## 6. 访谈要问的（比"你在意吗"有效）

你在计划里说要去问"你会在意自己会不会 JS 吗"。这个问法会得到礼貌答案。
换成 §3.3 那四问（行为题），并额外记一个字段：

> **他让 AI 写代码时，改代码的比例大概是多少？**（0% / 10% / 30% / 一半以上）

这个数直接决定 `dev_mode` 该怎么分档——如果 10 个受访者里 8 个说"改 30% 以上"，
那"纯 vibe"就是个伪需求，真正要做的是"AI 写 + 人改"这个混合模式。

## 7. 冻结期间明确不做的事

- 不改 `scoring.ts` / `combos.json` / `intake/*` / `explain/*`
- **不因为"新定位"就现在删 skills**——定位还没被验证，删了基线就不可比了
- 不凭想象写 36 条 AI 坑
- 不把这份文档里的模拟数字当成结论（它是"如果这么改会怎样"，不是"应该这么改"）
